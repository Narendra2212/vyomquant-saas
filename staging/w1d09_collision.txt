=== Q1. SCHEMA SCOPING PER DIMENSION ===
  A key like `relname` is unique only WITHIN a namespace. If a query is not
  schema-scoped, its declared key can collide across schemas.

  tables                         SCOPED
        nspname = literal=public
  columns                        SCOPED
        table_schema = literal=public
  primary_keys                   SCOPED
        nspname = literal=public
  foreign_keys                   SCOPED
        nspname = literal=public
  unique_and_check_constraints   SCOPED
        nspname = literal=public
  indexes                        SCOPED
        schemaname = literal=public
  row_level_security             SCOPED
        nspname = literal=public
  policies                       SCOPED
        schemaname = literal=public
  privileges                     SCOPED
        table_schema = literal=public
  extensions                     *** NOT SCHEMA-SCOPED ***
  functions                      SCOPED
        nspname = literal=public
  triggers                       SCOPED
        nspname = literal=public
  sequences                      *** NOT SCHEMA-SCOPED ***
  enum_types                     SCOPED
        nspname = literal=public
  alembic_version                *** NOT SCHEMA-SCOPED ***
  recorded_migrations            *** NOT SCHEMA-SCOPED ***

  dimensions with no detectable schema predicate: 4
      extensions
      sequences
      alembic_version
      recorded_migrations

=== Q2. recorded_migrations: is `filename` really unique? ===
  FULL QUERY:
      SELECT filename, sha256, step FROM public.schema_migrations
              ORDER BY filename, step

  ORDER BY wider than declared key (1)? -> ORDER BY (filename, step) = 2 terms: True
  Reading: an ORDER BY that adds `step` after `filename` is only necessary if
  more than one row can share a filename. If each file contributes one row per
  applied STEP, then (filename) is NOT unique and key width 1 is ambiguous.
